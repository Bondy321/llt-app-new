# Stable Identity Rollout Checklist

Use this checklist to validate opaque passenger identity ownership across restarts, migration, and verified login on multiple phones.

## Identity security contract

Passenger principals are random, server-issued values:

`pax_v2_{32 lowercase hexadecimal characters}`

The value is generated by `verifyPassengerLogin`, persisted in the server-only
`passenger_identity_security/{bookingRef}` branch, and contains no
booking reference, email, phone number, name, or other passenger data. It is already RTDB-safe; callers still use
`toRealtimeKeySegment()` at path boundaries for a consistent contract. Clients must never generate or bind a
passenger principal. New `pax_v1:` values are rejected by client validation, Database rules, and Storage rules.

Each phone verifies the booking reference and email with the server. The private security record uses
`deviceAuthorizationVersion: 2` and `authorizedAuthUids/{authUid}: true` for independently authorized installations.
Each installation receives its own session and participant row, while all phones for that booking keep the same
opaque passenger principal and shared booking-account content. A second verified phone does not replace the first.
Normal logout and session revocation affect only the captured installation/session.

Existing records without a device authorization version retain their exact `authorizedAuthUid` compatibility proof.
The next successful verified login atomically promotes that original UID and the requesting UID into the version-2
map without rotating the principal. Once version 2 exists, only a true map leaf grants device authorization; a retained
legacy scalar cannot bypass removal of that leaf. Unknown versions and `loginLocked: true` fail closed. Explicit
migration/security-review locks remain in force; enabling multiple phones does not remove them.

This security state remains separate from sync-owned booking credential records, so a booking refresh cannot erase
authorized phones or rotate the principal. Booking absence, email eligibility, canonical tour and current session
checks continue to apply independently on every phone.

Clients cannot read, create, replace or enumerate device authorization records. The server-owned account-deletion
workflow removes only the requesting phone's exact map leaf and matching legacy scalar; other phones retain access.
Deletion still removes shared passenger-principal app content under the existing account-deletion contract, which
the passenger confirmation explains. The older compatibility scalar-cleanup permission remains bounded to its owner.

## Production migration

Run the idempotent migration from `functions/` before deploying the stricter rules. Dry-run first:

```powershell
npm run migrate:opaque-passenger-identities
npm run migrate:opaque-passenger-identities -- --apply --confirm-project=loch-lomond-travel --backup=../outputs/security-backups/passenger-identity-pre-v2.json
```

The apply path reads only the bounded identity-bearing roots and commits one atomic RTDB multi-root update. It creates
the isolated passenger-security records, removes security state from sync-owned booking credential rows, and rewrites chat sender fields and actor keys, group/private photo
ownership and Storage object names, notification read state, presence, reactions, reports, safety data, profiles,
and bindings. It clears both access-grant roots, refreshes private-photo claims, revokes ambiguous sessions, moves
Storage objects before deleting legacy copies, and refuses to commit while any known exposed root still contains a
`pax_v1:` identity. The backup contains sensitive server data; keep it outside version control with restricted access.

## 1) Same device restart ownership persistence

**Goal:** Message ownership remains stable after app restart on the same device.

### Steps
1. Log in as a passenger and open a tour chat.
2. Send at least one new message.
3. Confirm the message writes `senderStableId`.
4. Force-close the app and relaunch it.
5. Reopen the same tour chat.
6. Verify the previously sent message still renders as owned by the same user.

### Firebase paths to inspect
- `users/{uid}`
- `identity_bindings/{stablePassengerKey}/{uid}`
- `identity_bindings_meta/{stablePassengerKey}`
- `chats/{tourId}/messages/{messageId}/senderStableId`

### Pass criteria
- `users/{uid}` has a `pax_v2_...` `stablePassengerId` containing no customer data.
- `users/{uid}` also has `stablePassengerKey = toRealtimeKeySegment(stablePassengerId)` and
  `privatePhotoOwnerKey` for private album rule checks.
- `identity_bindings/{stablePassengerKey}/{uid}` exists when identity persistence succeeds.
- Sent messages include `senderStableId`.
- Ownership rendering is unchanged after restart.

### Fail criteria
- `senderStableId` is missing for new messages.
- Ownership flips after restart.
- `users/{uid}` binding is absent or inconsistent.

## 2) Logout/login on the bound installation

**Goal:** Stable ownership remains correct after logging out and back in with the same account.

### Steps
1. Log in as a passenger and send a chat message.
2. Log out.
3. Log back in with the same booking/account.
4. Send another message in the same tour.
5. Compare ownership and stable IDs of old vs new messages.

### Firebase paths to inspect
- `users/{uid}`
- `chats/{tourId}/messages/{messageId}/senderStableId`

### Pass criteria
- Stable identity binding persists on `users/{uid}`.
- Both pre-logout and post-login messages resolve to the same ownership identity.
- New messages continue writing `senderStableId`.

### Fail criteria
- A new/different stable identity is unexpectedly generated.
- Message ownership diverges between sessions for the same account.
- A message is written without the expected stable sender identity.

## 3) Independent verified login on two phones

**Goal:** Two phones using the same valid booking reference/email share the stable account identity with independent sessions.

### Steps
1. On device A, log in and send a chat message.
2. On device B, attempt login with the same booking reference and email.
3. Confirm both phones receive different session IDs and the same opaque passenger principal.
4. Log out on B. Confirm A can still use the app and its session remains unchanged.
5. Log in again on B. Revoke B's exact session; confirm A still has access.
6. Verify wrong credentials, locked identities, source absence and missing email still fail on both phones.

### Firebase paths to inspect
- `users/{uid}`
- `chats/{tourId}/messages/{messageId}/senderStableId`

### Pass criteria
- Device B is admitted only after server credential verification.
- Device A retains its session, opaque identity and ownership scope.
- The response and logs contain no raw credential-derived identity.

### Fail criteria
- A phone receives a session with wrong credentials or without server admission.
- Logging out/revoking one phone invalidates another phone's session.
- An ambiguous migrated booking remains unlocked.

## 4) Private photo access after restart

**Goal:** Private photos remain accessible after restart using the stable owner path key.

### Steps
1. Log in as a passenger and open private photobook.
2. Upload at least one private photo.
3. Force-close and relaunch the app.
4. Reopen private photobook.
5. Confirm previously uploaded private photos still load.

### Firebase paths to inspect
- `users/{uid}`
- `private_tour_photos/{tourId}/{stablePassengerKey}`

### Pass criteria
- Photo records remain under `private_tour_photos/{tourId}/{stablePassengerKey}` and `userId` is the opaque `stablePassengerId`.
- Private album access can be authorized by either `identity_bindings/{stablePassengerKey}/{uid}` or
  the encoded owner fields on `users/{uid}` (`stablePassengerKey` / `privatePhotoOwnerKey`).
- Same user can still view photos after restart.
- `users/{uid}` remains bound to expected booking ownership metadata.

### Fail criteria
- Photos become inaccessible after restart.
- New session points to the wrong owner bucket.
- Ownership metadata in `users/{uid}` no longer matches expected booking.

## 5) Driver flow non-regression

**Goal:** Driver chat and related behavior are unaffected by passenger stable identity rollout.

### Steps
1. Log in as a driver.
2. Send group chat and internal chat messages.
3. Restart app and repeat messaging checks.
4. Verify driver ownership rendering and chat actions remain unchanged.

### Firebase paths to inspect
- `users/{uid}`
- `chats/{tourId}/messages/{messageId}/senderStableId`

### Pass criteria
- Driver chat functionality works before and after restart.
- No passenger-only stable identity assumptions break driver messaging.
- No regressions in internal or group chat sending.

### Fail criteria
- Driver chat send/retry fails after rollout changes.
- Driver ownership rendering regresses.
- Any new dependency on passenger stable identity breaks driver paths.
